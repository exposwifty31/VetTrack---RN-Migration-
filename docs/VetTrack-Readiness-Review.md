# PART I — CODE AUDIT (verify, don't trust)

## 1. VERDICT: YELLOW — proceed after named fixes

The migration is disciplined, honest about its own state, and the equipment-evidence pipeline is genuinely one system on the server. But judged cold against the stated bar ("two store submissions in review"), the RN app cannot ship today, and the plan itself says so. Decisive factors:

1. **Code Blue on RN is a placeholder, and the frozen ladder forbids shipping without it.** `rn-migration/src/screens/EmergencyScreen.tsx:1-6` is an explicit "coming soon" screen ("The Code Blue flows arrive in a later migration phase; this screen makes no pretense of emergency capability"). The Master Anchor's G4 no-go trigger is "Code Blue can't meet its frozen guarantees on RN" (`goofymappinghellman.md:478`). Only the offline emergency-block classifier exists (`src/lib/emergency-block.ts`, wired at `src/lib/auth-fetch.ts:120`, unit-tested).
2. **Native push does not exist anywhere.** The server's subscription validator rejects any non-URL endpoint — `vettrack/server/routes/push.ts:28` (`endpoint: z.string().url(...)`) — so an APNs/FCM device token cannot even be stored; the send library is web-push only (`server/lib/push.ts:1` imports `web-push`; `:178` `webpush.sendNotification`). No `ios.entitlements` (Critical Alerts) key exists in `rn-migration/app.json`.
3. **Store identity/compliance config is absent.** `rn-migration/app.json:11,22` still says `uk.vettrack.rnmigration` (plan requires `uk.vettrack.app`); there is **no `eas.json`**, no `scheme`/associated-domains/intent-filters (so the "QR/NFC deep links open the RN app" debug-spine item has zero config behind it), no privacy manifest, no `ITSAppUsesNonExemptEncryption`; account deletion is deliberately not shipped in RN (`src/lib/api/account.ts:21-27` documents the deferral; server endpoint exists at `vettrack/server/routes/users.ts:1363`).
4. **The G3 owner gate has never been run.** `rn-migration/docs/g3-results.md:206-219` — both daily-driver verdict lines read "… to be filled by the owner …". Everything downstream (G4, G5) is gated on this per the frozen ladder.
5. **Counterweight (why YELLOW, not RED): the unified evidence pipeline is real, wired, and tested on the server.** RFID ingest writes advisory columns and an outbox event in one transaction (`server/lib/rfid-ingest.ts:212-220, 503-505`); the anchor reducer is pure and contradiction-only (`server/services/equipment-anchor.service.ts:19-30`); custody toggles invalidate anchors and emit the same outbox (`server/services/equipment-custody-toggle.service.ts:348, 382-384`); the SSE spine is clinic-scoped with monotonic replay (`server/routes/realtime.ts:721-753, 800-801`); ~501 server test files include `rfid-gate-e2e.test.ts`, `room-sweep.integration.test.ts`, `code-blue-outbox-events.test.ts`.

## 2. BIG PICTURE

This is one coherent product, not stitched fragments: a single Express/Postgres backend serving four clients, with the RN app as a parallel successor client that deliberately consumes only frozen server surfaces. The equipment subsystem really is one evidence model — a per-clinic `equipment_anchors` table whose rows are created only by human-confirmed acts (return toggle, sweep confirm, citizen assert) and invalidated only by explicit contradictions (`checkout`, `rfid_elsewhere`, `sweep_missing`, `not_found_here` — `equipment-anchor.service.ts:7`), with machine evidence (RFID) confined to advisory last-seen columns and contradiction triggers, never anchor creation. The RN app is at G3: 23 screens, 73 test files, a hexagonal realtime port with cursor replay, NFC advisory scan wired per ADR-006 — but no Code Blue, no push, no offline write queue, no QR camera path, and pre-identity-migration store config. The two repos agree with their own documentation to an unusual degree; the plan under review (`tranquilprancingsprout.md`) made five specific code claims and all five verified true in source. The biggest architectural risk is not what's built but what's ambient: a placeholder emergency tab and web-only push in a product whose doctrine centers on emergency alerting. The biggest process strength is that nobody is pretending otherwise.

## 4. REAL-TIME REALITY CHECK

**Equipment pipeline, end-to-end (traced, complete — no break found):**

1. Controller POSTs signed batch → `server/routes/rfid.ts:49` (raw-body HMAC `:71-79`, clinic header `:50`, flag `:86`, schema `:92-97`).
2. `ingestRfidBatch` transaction: reads row insert + advisory `equipment` columns behind strictly-newer guard (`rfid-ingest.ts:212-220`) + `insertRealtimeDomainEvent(tx, {type:"EQUIPMENT_RFID_OBSERVED"})` in the **same transaction** (`:503-505`). Anchor contradiction (`rfid_elsewhere`) runs post-commit, fire-and-forget, non-fatal (`:243-277`).
3. `event-publisher` polls every 750ms, locks batch `FOR UPDATE SKIP LOCKED`, marks published, emits `clinic:<id>` (`event-publisher.ts:7,53-70`).
4. `GET /api/realtime/stream` (authed, clinic-scoped) writes the SSE frame with `id:` = monotonic outbox id; on reconnect, `Last-Event-ID` replays from the DB, and a pruned cursor forces full-snapshot resync (`realtime.ts:743-753,145`).
5. RN `SseAdapter` retains the cursor and re-sends it as an explicit header (`SseAdapter.ts:167`) — this also sidesteps the react-native-sse limitation that it can't seed `Last-Event-ID` natively.
6. The invalidation registry matches prefix `EQUIPMENT_` (`useEquipmentRealtimeSync.ts:32`) → `queryClient.invalidateQueries` → React Query refetch → re-render on Home / Equipment list / detail / My equipment / Alerts (deduped across mounts, `realtime-invalidation-registry.ts:1-27`).

**Where the chain legitimately stops:** backgrounded apps. `RealtimeBridge` closes the stream on background by design; with no native push (above), a backgrounded phone learns nothing until foregrounded. Acceptable for G3; fatal for the emergency story until G4-2/3 land.

**Room-sweep nuance (a correction to the plan's phrasing):** sweep results *do* propagate live — but only as an `audit_log` SSE row (`audit.ts:381-386`) that refreshes screens someone is already looking at (`rooms.ts:49`). There is no ALERT-level event and no push for `missingCount>0` (`docking.ts:598-606` ends at `logAudit`). "Dead" is accurate for *proactive alerting*, not for freshness.

**Code Blue:** server-confirmed, never optimistic — on RN this is vacuously true (no UI exists). On the frozen Capacitor client, mutations are awaited (`useCodeBlueSession.ts:209`), offline attempts throw `OfflineEmergencyMutationBlockedError` (`:6`), and session end is an awaited server call (`api.ts:1142`). The doctrine is enforced structurally in RN's fetch layer already (`auth-fetch.ts:107-124`): any Code Blue mutation that fails at network level throws loud, before any Code Blue UI exists to misuse it.

## 5. UNIFIED-TRACKING VERDICT

**Yes — on the server, QR/NFC/RFID/docking are one auditable evidence model, not four features.**

- (a) **Same evidence model:** both paths converge on `equipment_anchors`. Human acts create anchors (`docking.ts:563-570` sweep-confirm; return-toggle via `equipment-custody-toggle.service.ts`); human checkout and machine evidence alike invalidate them through the single reducer (`equipment-anchor.service.ts:19-30`), with a closed 4-reason union (`:7`). Reconciliation buckets (`docking.service.ts:74`) read the same rows.
- (b) **Machine evidence is advisory — enforced, not aspirational:** RFID never creates or overrides an anchor; it only updates separate advisory columns (strictly-newer, `rfid-ingest.ts:212-220`) and can contradict (`rfid_elsewhere`, `:243-277`). On the client, NFC reads pre-fill and never commit (`ScanScreen.tsx:13-15`). ADR-006 holds in code.
- (c) **Auditable:** every traced state change goes through `logAudit`, which double-writes the audit table and the outbox atomically (`audit.ts:361-386`); `actionType` is a closed union including `equipment_checked_out` (`audit.ts:27`) and `room_swept` (`:276`).

**Integration gaps:** (1) the `missing` bucket never alerts anyone proactively (above); (2) the without-human path is only as strong as deployed hardware — RFID/dock-sensor hardware is not deployed, so today the "ambient" leg is code-complete but evidence-empty; (3) RN has no QR leg at all and its NFC leg is hardware-unverified, so on the successor client the with-human path currently rests on manual search + custody toggles.

## 6. OVERKILL / SIMPLIFY

- **Escalation-ladder inversion:** a 3-stage, role-aware, idempotent escalation worker exists for *rooms not swept* (`sweep-escalation.worker.ts:2-35`) while the basic "equipment missing" alert doesn't exist. Simpler form: ship the plan's Phase-1 emit first; consider whether the full ladder could then be one nightly digest. Requirement served: accountability for sweep compliance — real, but sequenced backwards relative to value.
- **RFID secret rotation with exactly-once semantics and dual-secret grace windows** (`rfid.ts:60-85`, `server/lib/rfid/provisioning.ts`) before any reader hardware exists. Simpler: single secret + documented manual rotation until a second clinic or first real deployment. Requirement served: none yet in production.
- **Outbox DLQ machinery** — retry classification, backoff, auto-DLQ at 50 retries, admin DLQ routes + health routes (`event-publisher.ts:15-16`, `outbox-dlq-scanner.ts`, `routes/admin-outbox-dlq.ts`, `admin-outbox-health.ts`) for a single-node, same-process publisher whose only consumer is an in-memory emitter. Simpler: log-and-retry with a max, one metrics counter. Requirement served: durability of the frozen spine — defensible, but sized for a distributed system this isn't.
- **Directional-RFID hard-reject taxonomy** (R-M1.2a, `rfid.ts:19-43,106-112`) — a both-or-neither gateway-pair schema and a dedicated rejection error class for hardware that hasn't shipped. Simpler: accept direction as an optional string, resolve best-effort, log anomalies. Requirement served: determinism of a future ingest — premature.
- **Four separate staleness sweep workers** (`staleCheckoutSweepWorker`, `staleCheckInSweepWorker`, `stale-returned-sweep`, `staleTaskOwnershipSweepWorker`) with near-identical scan-then-notify shapes. Simpler: one parameterized staleness scanner with a rule table. Requirement served: each is real, the quadruplication isn't.
- **Planning-corpus ceremony** — a 624-line frozen anchor, pre-registration documents, blind-preference kits, per-slice skills-compliance sections. It demonstrably kept the repos honest (plan claims all verified), so this is working overhead — but it is the single largest source of onboarding cost, and G4/G5 could halve the ritual without losing the gate discipline. Requirement served: auditability of decisions — genuinely, if expensively.
- **Not overkill (checked and cleared):** the hexagonal realtime port in RN (it's what makes the SSE adapter testable without sockets); the anchor reducer's purity (it's 12 lines); the outbox+cursor pattern itself (standards-backed; see Part II B3).

## 2. Five verdict answers

**1. Big picture.** Yes — this matches how comparable systems are actually built in 2026. The RN stack is the current, officially recommended configuration (SDK 57 / RN 0.86.2 / React 19.2.3 / New Arch mandatory / CNG), not an exotic bet. The tracking architecture (human-confirmed authority, advisory ambient reads, audit trail) is the same split real hospital RFID/RTLS deployments use. The main deviation from industry norm is favorable: unusually strict gating discipline and unusually honest self-audit.

**2. Internal consistency.** The A/B/C choices are mutually compatible and current per official docs; the version triple is exactly Expo's own SDK 57 template pin. Two frictions, no contradictions: React's patch line has moved to 19.2.8 (freeze policy accepts this), and `react-native-sse` (1.2.1, March 2024) is a stale dependency mitigated by the in-house adapter but worth an eventual fork-or-vendor decision. The C-claims (Critical Alerts, immutable channels, full-screen-intent limits) are all accurate, which means the plan's "Android urgency decision before channel creation" (G4-0b) is not ceremony — it is forced by a real one-way door.

**3. Real-time reality.** Documented platform behavior says foreground SSE + native push wake-up is the only workable emergency design on mobile — WebSockets would face identical backgrounding constraints. VetTrack's architecture already assumes exactly this (SSE foreground catch-up with cursor replay; push as notification-only per ADR-009), so the design is right; the gap is that the push half is unbuilt (Part I, factor 2). Known failure modes to design around: react-native-sse's no-recovery-after-sleep (already handled by AppState-driven reconnect), no reconnect backoff (mitigated by disabling library reconnect), and the `retry:`-line latent coupling (recommend a server-side guard test).

**4. Overkill.** Against industry norms: four-modality tracking for a single practice is ahead of need at deployment level, but the code sequencing already defers the expensive parts (hardware undeployed, dock sensor design-only) — so the practical overkill lives in server ceremony, not hardware: RFID secret-rotation machinery and directional-rejection taxonomy before any reader exists, DLQ/admin surface sized for a distributed system on a single-node publisher, four near-identical staleness workers, and an escalation ladder for unswept rooms while the basic missing-equipment alert is absent (see Part I §6 for simpler forms).

**5. Intent vs external reality — stale/mistaken assumptions.** The plan's external assumptions held up remarkably well; corrections found: (a) iPhone screenshots may be 6.5" or 6.9" — 6.9" is not compulsory; (b) CSE7766 is not a "better chip" for low loads — only ADE7953-class qualifies; (c) target API 36 becomes binding 2026-08-31 (Nov 1 with extension) — imminent, not distant; (d) new external change not in any plan: Google's developer-verification expansion and Play Console requirements refresh effective 2026-09-30; (e) Apple's new age-rating questionnaire (deadline was 2026-01-31) must be completed for the inherited listing; (f) the $75 import exemption survived a revocation attempt but VAT still applies above it — pilot pricing should not assume tax-free.

## Synthesis

The version stack checks out exactly as stated. Expo SDK 57 is the current released SDK (`expo@57.0.11` on `latest`, with 58 existing only as a canary build), and its official blank template pins `react-native@0.86.2` and `react@19.2.3` — the precise pairing claimed, and RN 0.86.2's own peer dependency is `react: ^19.2.3`. The only nuance is that React has since moved to 19.2.8, so 19.2.3 is the Expo-pinned patch rather than the newest React. The New Architecture question is settled rather than in-flight: RN 0.82 (October 2025) was the first release running entirely on the New Architecture with no opt-out, the legacy architecture was frozen in June 2025, and Expo made it unconditional from SDK 55 — so "Bridgeless is mandatory" is simply the status quo on SDK 57, not a migration risk. CNG likewise is the documented default posture ("we highly recommend using Prebuild", `ios`/`android` gitignored in new projects, EAS Build prebuilds when they are absent), with real but well-documented caveats around overwritten native edits, non-idempotent config plugins, brownfield projects, and libraries lacking config plugins; SDK 57 further tightened this by making `expo prebuild` clean by default.

The SSE half of the stack is where the diligence risk sits. React Native ships no built-in `EventSource`, so a library is genuinely needed, but `react-native-sse` is coasting: its last npm publish was March 2024 and its last commit July 2025, with an open issue asking it to comply with the `EventSource` specification, no way to seed `lastEventId` on the initial connection, fixed-interval reconnects with no backoff or jitter, and a standing report that the connection aborts on app-switch and cannot recover without a restart. Its own README concedes that it neither detects nor recovers from connection loss during app sleep. That limitation is not really the library's fault — Apple's docs state apps get no extra execution time after backgrounding and are moved to a suspended state whose scenes can be disconnected at will, and Android's Doze explicitly "suspends network access" while App Standby defers background network for idle apps. Neither platform exempts WebSockets, so the SSE-vs-WebSocket choice does not change the background story; it only changes foreground ergonomics. For emergency-grade timeliness, both vendors point to the same answer: an FCM high-priority message or an APNs `content-available` background push as the wake-up (30 seconds of runtime on iOS, coalesced to the newest message), with the payload carrying enough information to be actionable on its own. Finally, the resilience design is sound and standards-backed: the transactional outbox is a canonical pattern documented by both microservices.io and Microsoft's Azure Architecture Center, and WHATWG's HTML Standard specifies exactly the `id` / `Last-Event-ID` replay-from-cursor mechanism the design relies on. The composite is not a single named pattern, and the chosen client library will need an application-level shim to send the cursor on the first connect — but architecturally the approach is correct rather than overkill.

## 2. Synthesis

**Push/notification claims (C1–C4) hold up.** The due-diligence document's model of the platform asymmetry is accurate: iOS has a genuine, Apple-gated escalation path (the Critical Alerts entitlement, requested via form, scoped by Apple's own guidance to health/safety and government-grade use cases), while Android has no equivalent. Android's only DND-bypass lever, `NotificationChannel.setBypassDnd()`, requires user-granted Notification Policy Access and is void once the user has touched the channel — and Android 15 removed global DND manipulation entirely in favour of `AutomaticZenRule`. Any product design that assumes symmetric "critical alert" delivery across iOS and Android is wrong at the platform level, not merely at the policy level.

**Channel immutability (C3) is a hard architectural constraint, not a policy risk.** Importance, sound, vibration, lights and channel-group binding are frozen at `createNotificationChannel()`. The only remediation path is shipping a *new* channel ID (and thereby resetting the user's prior customization), so notification taxonomy needs to be right at first launch. Name and description remain mutable.

**Full-screen intents (C4) are the single largest push-delivery risk for a non-calling, non-alarm app.** The restriction is stable — nothing changed in Android 15 or 16 — but the enforcement is now fully live (Play Console declaration since May 31, 2024; default grant restricted to calling/alarm since January 22, 2025) and the failure mode is silent: the notification quietly degrades to a heads-up banner. Apps must call `canUseFullScreenIntent()` and deep-link to `ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`, and Play states the permission request is subject to review.

**Store-policy claims (D1–D7) are broadly current, with two corrections and one timing nuance.**
- *Correction 1 (D7a):* Apple does not strictly require 6.9-inch iPhone screenshots — one iPhone set at **either** 6.9" or 6.5" suffices; only the 13" iPad set is unconditionally required (when the app runs on iPad). Add the 2026-07-08 no-alpha-channel rule to any asset checklist.
- *Correction 2 (C1 caveat):* the "Apple approval that can be denied" phrasing cannot be sourced to a primary Apple page in this session — the entitlement request form is login-gated. The entitlement and the request-form gate are confirmed; treat "can be denied" as a reasonable but unsourced inference.
- *Timing nuance (D2):* API level 36 is **not yet in force** on the verification date. August 31, 2026 is the switch-on date for new apps and updates, with a Play Console extension path to November 1, 2026. A build submitted today still only needs API 35, but any release train extending past end-of-August must be on API 36.

**The biggest forward-looking item not in the original claim set is D3's scope expansion.** Google's developer verification is no longer a Play-only concern: from **September 30, 2026** Android developer verification begins regional enforcement for select stores, covering apps distributed **outside** Google Play, with package-name registration, D-U-N-S and website verification for organizations, possible government ID upload, and a free Limited-distribution tier capped at 20 user-authorized devices. Any diligence on distribution strategy — sideloading, enterprise side channels, alternative stores — should be re-run against that date, and the refreshed "Play Console Requirements" article carries the same September 30, 2026 effective date.

**Net:** of the eleven assessed items, nine are CONFIRMED as stated, one (D7a iPhone screenshots) is partially wrong in its "required" framing, and one sub-clause (C1 "can be denied") is UNVERIFIABLE from primary sources. No claim was found to be OUTDATED or OVERKILL.

## 2. Synthesis

**E — the RTLS practice pattern is orthodox, and the multi-modal stack is defensible but scale-sensitive.**

The "ambient reads advise, human scans confirm, everything is logged" pattern is not a novel design — it is the explicit position of the healthcare auto-ID field. The clearest single statement is ID Integration's FAQ: *"Does RFID replace barcode? No. Barcode remains the identifier. RFID adds automated custody and location"* ([ID Integration, 2025-10-14](https://id-integration.com/no-specimen-left-behind-passive-rfid-specimen-tracking-for-hospitals-and-idns/)). The federal-guidance side agrees on the confirming act: ONC's SAFER patient-identification guide asks organizations to scan a barcode or RFID wristband *"at key points of patient care"* and to keep a manual backup for equipment failure ([HealthIT.gov SAFER Guide 6](https://healthit.gov/wp-content/uploads/2025/01/Safer-Guide-6.-Patient-Identification-Final.pdf)).

The empirical justification is stronger than the rhetorical one. The JAMIA multidimensional RTLS evaluation found continuous positional accuracy of **≥2 m in a 2.5 m hallway**, with the system routinely placing a tracked person in the wrong room, and nurses reporting assets *"quite distant from the location shown by the system"* ([Okoniewska et al., JAMIA 19(4):674–679, 2012](https://pmc.ncbi.nlm.nih.gov/articles/PMC3384113/)). The same study found **100% accuracy with zero false positives** on threshold/portal enter-exit events and on 26 simulated inventory-removal events. That asymmetry is the technical basis for the whole pattern: **portal/dock crossings are trustworthy events; continuous position is a hint.** Even the best vendor numbers concede residual error — Impinj markets RAIN RFID inventory accuracy as *"over 95%"* ([Impinj, 2021-06-10](https://www.impinj.com/library/blog/healthcare-inventory-and-asset-management-optimize)), which is excellent for cycle counting and unacceptable as a sole custody record.

On over-engineering: a stack of QR + NFC + UHF RFID + dock sensors is *architecturally* mainstream. The VA's VISN 11 program ran **six different RTLS technologies plus passive UHF, passive HF, and 255,000 barcode-etched instruments** on one platform ([RFID Journal](https://www.rfidjournal.com/news/veterans-affairs-implementing-rtls-across-seven-midwest-hospitals/83885/)), and current vendors still sell explicitly hybrid BLE-RTLS + passive-RFID architectures ([Penguin × Zebra, 2025-10-09](https://penguinin.com/penguin-location-services-and-zebra-technologies-partner-to-deliver-end-to-end-asset-visibility-in-healthcare-rtls/)). The caution is organizational, not technical: Fisher & Monahan found *"serious obstacles to effective deployment due to the material and organizational constraints of the hospitals themselves"* and that workable asset tracking needs whole-facility deployment with centralized ownership ([2012-10-05](https://pubmed.ncbi.nlm.nih.gov/22857790/)). For a single veterinary practice, four modalities is likely one or two more than the operation can maintain — the honest verdict is *normal at enterprise scale, over-engineered at practice scale.* No veterinary-specific primary guidance was locatable; that gap should be stated rather than papered over.

**F — the hardware call is correct, and the datasheets are unusually blunt about why.**

The HLW8032's advertised "±0.2% active power over 1000:1" is a full-scale-referenced number, not a low-load promise. Its own application guide states a **40 mA minimum test current** and only 2% factory accuracy ([Hiliwei App Guide REV 3.0](https://images.tuyacn.com/smart/Hardware_Developer/hardware_data/Electricity_Statistics/hlw8032/HLW8032Application_Guide_V1.0.pdf)); the module FAQ states a **50 mA–10 A** range, that non-zero current at no load is *"expected behavior"*, and that no-load detection takes ~5 s while a ~3 W reading takes ~8 s to settle ([ElectroDragon, 2024-12-08](https://w2.electrodragon.com/Chip-cn-dat/HLW-dat/HLW8032-dat/HLW8032-faq-dat.md)). Tasmota's documentation names HLW8032 and CSE7766 together as *"occasionally report[ing] invalid power measurements for load values below 5W"* and ships a switch whose stated purpose is to **discard all loads below 6 W** ([Tasmota](https://tasmota.github.io/docs/Power-Monitoring-Calibration/)). The maintainer's advice is unambiguous: *"If low loads (<5W) are common I suggest not to use this energy monitoring device… There are better monitoring devices like ADE7953"* ([Tasmota Discussion #18474, 2023-04-21](https://github.com/arendst/Tasmota/discussions/18474)).

The claim that the CSE7766 is *better at low load* than the HLW8032 does not survive its own datasheet: **50 mA minimum measured current, 38 mA no-load current, 2 W minimum measured power, and ±1.5 W max absolute error below 15 W** ([CSE7766 Rev1.2, 2017-08-10](https://itead.cc/wp-content/uploads/2022/05/CSE7766.pdf)) — the same class of blindness, and ESPHome hard-codes the 50 mA note in the driver ([cse7766.cpp](https://api-docs.esphome.io/cse7766_8cpp_source)). The ADE7953 genuinely is a tier up: 0.1% over **3000:1**, IEC 62053 / EN 50470 metrology compliance, and a purpose-built programmable no-load threshold defaulting to roughly **10,000:1** to kill meter creep ([ADE7953 Rev. C, 12/2016](https://www.analog.com/media/en/technical-documentation/data-sheets/ADE7953.pdf)). But even ADE7953-class plugs are reported reading 0 W at 0.6 W and ~30% off in the 4–5 W band ([HA Community, 2024-08-06](https://community.home-assistant.io/t/power-monitoring-smart-plug-accurate-under-1w/757154)). **No mains power meter in this price class is a presence sensor for a small idle device.**

Against that, the SNZB-04P is the correct primitive: Zigbee 3.0 on an EFR32MG22, magnet proximity at ≤20 mm, CR2477 with a vendor-claimed 5+ year life, ~$10–16, CE/FCC/ISED ([SONOFF](https://support.sonoff.tech/snzb-04p-usermanual/) / [SONOFF store, 2025-05-21](https://sonoff.tech/products/sonoff-zigbee-door-window-sensor-snzb-04p) / [Seeed, $9.99 @10+](https://www.seeedstudio.com/SONOFF-SNZB-04P-Zigbee-Door-Window-Sensor-p-6364.html)), running fully locally through Zigbee2MQTT with `contact`, `battery`, `voltage`, `battery_low`, `tamper` and OTA ([Zigbee2MQTT](https://www.zigbee2mqtt.io/devices/SNZB-04P.html)), *"without the vendor's bridge or gateway"* ([Zigbee2MQTT README](https://github.com/koenkk/zigbee2mqtt)). The tamper channel is a genuine design bonus: it catches the "remove sensor and magnet together" evasion that contact state alone misses ([SONOFF](https://sonoff.tech/nl-nl/products/sonoff-zigbee-door-window-sensor-snzb-04p), 2025-05-21).

**Bottom line:** E1's practice pattern is confirmed and well-supported; the four-modality stack is confirmed as an existing architecture but is over-engineered for small-practice scale; E2 is confirmed with the practical caveat that iOS background scanning requires URI-record encoding; F1 is confirmed in detail; F2 is confirmed; F3 is split (ADE7953 yes, CSE7766 no); F4 is confirmed as the correct engineering call.

## 2. What continuous staff-area video monitoring in an Israeli veterinary clinic actually requires

Derived from [PPA Guideline 5/2017](https://www.gov.il/blobfolder/policy/workplace_camera/he/3-17_0.pdf), [PPA Guideline 4/2012](https://www.gov.il/BlobFolder/legalinfo/surveillance_cameras_guidelines/he/The%20use%20of%20security%20cameras_2025.pdf), the [March 2025 National Labour Court ruling](https://herzoglaw.co.il/he/news-and-insights/%D7%94%D7%96%D7%9B%D7%95%D7%AA-%D7%9C%D7%A4%D7%A8%D7%98%D7%99%D7%95%D7%AA-%D7%95%D7%A9%D7%99%D7%9E%D7%95%D7%A9-%D7%91%D7%9E%D7%A6%D7%9C%D7%9E%D7%95%D7%AA-%D7%91%D7%9E%D7%A7%D7%95%D7%9E%D7%95%D7%AA/), and the [gov.il Amendment 13 guide](https://www.gov.il/BlobFolder/reports/guide_tikon13_professional/he/tikun%2013%20_170825.pdf):

1. **Document a specific legitimate purpose** per camera (e.g. protecting staff/clients, protecting controlled drugs and equipment, securing sensitive systems). Generic "monitoring staff" without a defined purpose fails stage 1 of the Labour Court test.
2. **Run and record a proportionality assessment**, including less-intrusive alternatives, and calibrate coverage, camera count, filming hours, resolution and retention period.
3. **Write a camera policy** covering manner, scope and purposes; present it to staff on an ongoing basis; refresh it periodically.
4. **Consult employees or their representatives** before finalising the policy (consultation, not negotiation).
5. **Notify staff in writing**, in detail, before deployment; add a camera annex to employment agreements or a standalone document for new hires. Post **signage** in client-facing areas.
6. **Obtain explicit consent scaled to intrusiveness** — notice suffices for low-intrusion public areas; explicit written consent is required where cameras face a personal workstation; **no consent validates** cameras in toilets or changing rooms.
7. **Do not deploy covert cameras.** Covert filming of employees may be a criminal offence; narrow exceptions require concrete suspicion of serious offences, senior-management approval and a prior reasoned legal opinion.
8. **Avoid continuous filming of staff-only rest areas** (kitchenette, break room) and personal workstations. This is the exposure that produced a severance award in *Friedman v. Elkaner*.
9. **Enforce purpose limitation** — security footage may not be repurposed for productivity or break-time discipline.
10. **Treat the recording system as a database** under the Data Security Regulations 2017: database-definition document, information-security procedure, access authorisations and logging, staff confidentiality undertakings, defined retention with auto-deletion, vendor/DPA contracts (Reg. 15), and prompt PPA reporting of severe security incidents (Reg. 11(d)) — the exact duty that produced the first NIS 256,000 fine in July 2026.
11. **Handle access requests** from filmed employees under §13 of the Law (footage of others blurred or viewed on premises).
12. **Not required:** database registration (abolished for private-sector DBs) and, on these facts, DPO appointment.

## 3. Synthesis

**G1 is broadly accurate and, if anything, understated on the legal-framework side but overstated on the imminence of regulatory fines.** Amendment 13 was passed by the Knesset on 5 August 2024 and entered into force on 14 August 2025, giving Israel's Privacy Protection Authority genuinely new teeth: routine supervision without suspicion, a formal administrative-inquiry track with court-backed search and computer-penetration powers, and — for the first time — direct administrative monetary fines under the Law, the Data Security Regulations and the EEA Regulations, capped at 5% of annual turnover with formula-driven per-data-subject amounts and up to 70% reductions for cooperation. In practice enforcement has been slow and healthcare-focused: cross-sector audits opened on 10 December 2025 (local authorities, online commerce, popular apps, genetic-screening institutes, after-school childcare — veterinary clinics are not targeted) and the first-ever fine landed only on 21 July 2026, NIS 256,000 against Meuhedet Health Fund for late breach reporting. Workplace camera surveillance is nonetheless a real and *increasing* risk, but the sharpest edge in 2026 is the labour courts, not the PPA: the National Labour Court's 26 March 2025 *Friedman v. Elkaner* judgment converted the PPA's previously non-binding 2017 camera guideline into enforceable law and awarded constructive-dismissal severance to a veteran employee continuously filmed at her workstation without explicit consent. For a veterinary clinic, continuous video monitoring of *staff areas* specifically is the highest-risk configuration in Israeli law and does require concrete compliance steps — documented purpose, proportionality assessment, written policy, employee consultation, advance written notice, consent scaled to intrusiveness, purpose limitation, no covert cameras, and full Data Security Regulations treatment of the recording system. What it does *not* require is database registration (abolished for the private sector) or a DPO (the clinic does not meet any of the four statutory triggers) — claims to the contrary would be overkill.

**G2 requires a correction and a caveat.** The claim that personal imports are VAT-exempt to USD 75 with customs relief to USD 500 is **currently correct as of 10 August 2026**, but only after an unusually volatile eighteen months, and the "purchase tax exempt to $500" element is wrong. The statutory hook is item 98.02 of the Customs Tariff, Exemptions and Purchase Tax Order 2017. Finance Minister Smotrich raised the ceiling from USD 75 to USD 150 effective 24 December 2025; the Knesset struck that down 59–25 on 23/24 February 2026; he immediately signed a USD 130 replacement; the Chambers of Commerce petitioned the High Court, which declined to rule on 5 May 2026; and the Knesset struck the second order down 59–23 on 1 June 2026, with the USD 75 threshold restored in customs systems on 2 June 2026. No reform ever *eliminated* the $75 exemption — every attempt was to enlarge it, and every attempt failed. Three operational details matter for any diligence model: eligibility is tested on goods value only (shipping and insurance excluded if separately itemised), but once the threshold is crossed VAT at 18% applies to the *entire* CIF value rather than the excess; in the USD 75–500 band only customs duty is waived, so purchase tax still bites on categories such as entertainment electronics and vehicle spare parts; and the controlling date is customs release, not order date. Given four threshold changes in six months and active litigation history, any figure quoted here should be re-verified against the Israel Tax Authority import-tax calculator before commercial reliance.

Real-Time Reality Check
The backend evidence confirms one clean end-to-end propagation pattern for Code Blue: a session start writes the session row and two outbox rows (NOTIFICATION_REQUESTED, CODE_BLUE_STATUS_CHANGED) inside a single Postgres transaction guarded by an advisory lock, then triggers invalidateActiveCodeBlueCache(clinicId) so the next SSE keepalive tick reflects the change within a documented five-second bound, and separately enqueues a push notification job — all after the transaction commits, never before. This is a server-confirmed, non-optimistic design: the HTTP response is only returned after the DB transaction succeeds, and the manager-eligibility evaluator runs before any side effect commits, with fault-open behavior gated by explicit reason-code branching. For the RFID/ambient path, the ingest endpoint validates HMAC and clinic-scoping before touching ingestRfidBatch, and rejects undecidable directional payloads with a 422 rather than writing garbage state — consistent with "machine evidence must never silently degrade." However, this review could not trace the outbox row all the way to a live SSE broadcast and RN client re-render because lib/event-publisher.ts, routes/realtime.ts, and the RN react-native-sse consumer were not opened in this pass; that hop is UNVERIFIED, not confirmed broken.

Unified-Tracking Verdict
At the write layer, Code Blue and RFID both terminate in the same vt_event_outbox table via the same insertRealtimeDomainEvent() helper, which is genuine evidence for "one evidence model" rather than four siloed features.
